# Authenticate Protected Routes Through a Wrapper That Injects the Personal Album

Protected API routes will authenticate through a single `withAuth` wrapper created by a factory that receives the Personal Album store. The wrapper parses and verifies the Session cookie, short-circuits unauthenticated requests with 401, and calls the route core with the authenticated User **and** their `PersonalAlbum` handle. Route cores therefore never see an unauthenticated user and never resolve the album themselves — the User-to-album pairing from ADR-0019 happens in exactly one place instead of once per handler. We considered a wrapper that injects only the User, but that leaves the pairing repeated at every call site, which is the duplication this decision exists to remove.

Sign-In Code records live behind their own small `SignInCodeStore` (create, get, delete — storing a code hash, never the plain code) rather than being folded into the Personal Album store, confirming the exclusion recorded in ADR-0019: they share the DynamoDB table but have a different lifecycle and a single caller. Code hashing, expiry checks, and timing-safe comparison stay in the session route cores — the storage adapters remain policy-free so the in-memory fake cannot drift from the real adapter's behavior.

Session routes themselves are not wrapped: `GET /session` must answer `{signedIn: false}` rather than 401, and the sign-in endpoints serve unauthenticated users by definition. The two sign-in cores receive their nondeterminism (clock, code generator, id generator, email sender) as injected dependencies, following the pattern already used by Create Upload Batch, so their security behavior is assertable in tests.
