# Own Album Mutations in a Shell-Level Module

Archive Photo, Restore Photo, Retry Processing, and Original Download are all invoked from Photo Viewer's More menu, so the obvious home for them is `PhotoViewer` — which already knows the current Photo and its neighbours, and could therefore archive and advance atomically. The Web client will instead own them in one shell-level `albumMutations` deep module, held above the router alongside the browsing history registry, with its own port and in-memory test adapter. The deciding constraint is lifetime, not layering: ADR-0056 makes `PhotoViewer` an independent read module created per opened Photo and **disposed on close**, while the accepted design requires `Photo moved to Archive — Undo` to survive for eight seconds, across route changes, after the Viewer that triggered it has advanced or closed. State owned by `PhotoViewer` cannot outlive the Viewer, so option one is structurally unable to hold the behaviour the design specifies, and orchestrating it inline in `PhotoViewerRoute` would put optimistic bookkeeping, rollback, registry invalidation, and Date Index staleness into a route adapter.

`albumMutations` therefore owns the optimistic apply, the request, rollback on failure, and the membership-change events that the shell feedback region and the browsing history registry subscribe to. It also gives Retry Processing and Original Download an existing seam instead of two further ad-hoc call sites. One consequence is deliberate and worth recording: on failure the module rolls back **membership but not navigation** — the Photo reappears at its exact index and a persistent, retryable message names it, but the Viewer is not yanked back to the Photo the User has already moved past, because a late backwards jump is more disorienting than a message.
