# Recover the Upload Tray from a Session-Scoped Batch ID

Upload Tray must recover a recently active Upload Batch after Original Photos finish transferring and server processing continues, while remaining explicitly not durable Upload Batch history. The Web client will satisfy both by persisting **only** the `uploadBatchId` and a timestamp, keyed by User ID, in `sessionStorage`, and rehydrating from `GET /upload-batches/{uploadBatchId}` on load. Only the id is stored because the status read already returns file name, Processing State, Exact Duplicate, and failure code per Photo, so persisting file names would copy private album content into browser storage to save nothing — and this is the app's first client-side persistence of any kind, so it inherits ADR-0062's obligation to dispose private client state on Session loss. `sessionStorage` is chosen over `localStorage` because tab lifetime *is* the recovery boundary the design describes: the User reloaded or came back to the tab, not the User returned tomorrow, which avoids owing a cross-session cleanup story at all.

Rehydration is gated twice. The stored timestamp must be within roughly thirty minutes, which merely avoids issuing a request for an obviously dead id and bounds a batch wedged non-terminal forever; the real condition is that the recovered batch must still contain at least one Photo in Upload Requested or Processing, which is exactly the design's "server processing continues". A batch that returns fully terminal has its key cleared silently and shows no Tray, because presenting a completed summary the User already dismissed is durable Upload Batch history wearing a Tray costume. A server-side "recent batches" query was rejected for the same reason: it is how that forbidden history gets built by accident.
