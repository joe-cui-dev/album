# Encapsulate Each Browsing Window in One Deep Module

The web client will implement each history entry's Browsing Window through one deep module identified by an opaque per-history-entry instance key. Collection and start anchor configure a new instance but do not identify it. The module owns its cursor chain, Photo de-duplication, compact descriptors, incomplete row tail, Thumbnail Access leases, viewport demand, failures, restoration anchor, and responsive reflow policy. Its small external interface exposes a subscribable, read-only, render-ready layout snapshot and does not mutate routes or expose raw exceptions. The UI surface is limited to `getSnapshot`, `subscribe`, one library-neutral viewport observation carrying width, visible items, focus, scroll origin, and any restoration acknowledgement, one lease-revisioned thumbnail outcome observation, and one semantic collection Retry intent. It does not expose `loadMore`, access acquisition or renewal, anchor recording, cursors, or Photo-ID demand commands. Lifecycle operations are reserved for the browsing-history registry. Before any layout exists, a collection-read failure appears as a render-ready `initial-failure`; after rows exist, it appears as a `tail-failure` that preserves them; an exhausted per-Photo Thumbnail Access recovery appears only as that cell's placeholder and never promotes to a collection failure. Offline is instead a non-blocking suspension state: the module preserves completed content and unexpired leases, starts no collection or access request, does not classify requests cancelled or rejected across the transition as failures, and automatically re-evaluates demand when online returns. The snapshot may expose `offline` for presentation without requiring a Retry. The UI owns copy and styling, while one semantic collection Retry intent clears a genuine paused failure and re-evaluates current viewport demand without accepting cursors or Photo IDs. The snapshot hides descriptor, withholding, lease, expiry, and backoff maps. Its Justified Rows contain cells that already combine stable geometry, Photo link information, and current ready, loading, placeholder, or withheld presentation, with structural sharing preserving unchanged rows when access state changes. The Browsing Window maps viewport facts to Photos and owns width-change coalescing, layout recomputation, anchor-preserving scroll correction, revision acknowledgement and supersession, soon-visible policy, load demand, Thumbnail Access demand, temporary-URL retention, and restoration decisions. It serialises collection reads to at most one in-flight request, coalesces repeated demand, and keeps reading from the retained cursor until the soon-visible range is covered, the collection ends, or a failure pauses automatic paging. A render-ready tail state exposes that failure, and a User retry intent clears it and re-evaluates current demand rather than commanding a specific page read. The lease scheduler, restoration resolver, and count-bounded LRU are private implementation modules or internal test seams, not additional public modules that callers coordinate. The primary behavioural test surface remains the Browsing Window interface with deterministic time, network, lifecycle, and viewport observations; focused internal tests are reserved for pure algorithms. Existing coordination tests that reach through the boundary will be replaced, rather than duplicated, by interface-level sequences spanning viewport demand, access, renewal or failure, restoration, and lifecycle. Pure layout and policy algorithms retain focused unit tests, while a small Playwright layer verifies the real virtualizer, DOM focus, and browser-history integration. An owned album-browsing port at the internal network seam has an HTTP adapter for production and an in-memory adapter for tests, while Justified Row computation remains a pure internal seam. This concentrates ordering and race rules behind one test surface instead of requiring route elements to coordinate a cluster of shallow React hooks.
