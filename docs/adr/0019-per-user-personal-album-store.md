# Access Photo Metadata Through a Per-User Personal Album Store

All DynamoDB access for Photo records, Timeline items, and Upload Batch records will live behind a single store module in `apps/api`, exposed as a per-User handle: `store.personalAlbumOf(userId)` returns a `PersonalAlbum` whose methods take no user parameter. This makes the ADR-0011 ownership boundary structural — handler code cannot address two Users' data in one call — and gives the `TIMELINE#` write/read contract, the DynamoDB key formats, and a single authoritative Photo row validator one home instead of being repeated across seven handler files. Sign-in code storage is deliberately excluded: it shares the table but belongs to the session and auth seam, which has its own lifecycle and single caller.

The store exposes intent verbs (`createPhoto`, `createUploadBatch`, `markProcessingStarted`, `markProcessingFailed`, `markExactDuplicate`, `markReady`, `archivePhoto`) rather than a generic update, so transition invariants such as clearing failure fields on success live in one implementation. `markReady` also writes the Photo's Timeline item, making "a ready Photo has a Timeline item" (ADR-0016) a store guarantee instead of a per-caller obligation.

Two adapters satisfy the interface: the DynamoDB adapter used in Lambda, and an in-memory fake used by handler tests and available for local development. A contract suite (round-trips, state transitions, timeline range queries, cross-User isolation) runs against the fake; the DynamoDB adapter has a command-assertion suite against a stubbed DocumentClient, avoiding a dynamodb-local dependency.

Deliberately unchanged in the first version: writes carry no ConditionExpression state guards, matching pre-store behavior, and Timeline items stay thin — the timeline read still fans out to Photo reads inside the store (batched, no longer sequential). Removing that fan-out by denormalizing Timeline items is a future decision that would change only this module's implementation, invisible to callers.
