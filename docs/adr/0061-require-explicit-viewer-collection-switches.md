# Require Explicit Viewer Collection Switches

A contextual Viewer bootstrap whose requested source collection no longer contains the Photo will return a structured `photo_collection_changed` conflict rather than silently replacing the originating Viewer Sequence. The client explains whether the Photo moved to Trash or Timeline and offers an explicit switch to the current collection or a return to the source view. A direct Viewer URL without source context still infers the Photo's current collection.

`currentCollection` answers a membership question -- where does this Photo belong now -- so it is typed `MembershipCollection` (`active` \| `trashed`), never `favourite`. Favourites is not a place a Photo currently *is* in this sense: a Photo can be favourited and simultaneously belong to `active` or `trashed`. Requesting `collection=favourite` from a contextual bootstrap validates "still favourited AND not trashed"; on failure it returns the same `photo_collection_changed` conflict carrying `active`/`trashed`, and the client supplies its own wording because it knows it asked for Favourites. A direct Viewer URL without source context never infers `favourite` for the same reason a direct URL infers nothing else about how the User got there -- there is no source collection to fall back to, and inferring one risks a Viewer Sequence built against the wrong neighbours.

This preserves the rule that one Viewer Sequence never crosses collections while allowing live changes from another device to recover without a misleading neighbour change.
