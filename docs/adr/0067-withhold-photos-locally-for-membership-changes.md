# Withhold Photos Locally for Membership Changes

Archive Photo and Restore Photo must take effect immediately in the Browsing Window the User is looking at, stay exactly reversible for the duration of Undo, and never reflow a displayed row. The Web client will therefore apply a membership change by **withholding** the Photo rather than removing it: the compact descriptor stays in the window's ordered array and Justified Row layout skips it, so Undo simply stops withholding and the Photo reappears at the identical index. Removing and re-inserting the descriptor was rejected because re-deriving the insertion point would duplicate the Timeline ordering rule — precision-boundary grouping, then Added At, then Photo ID — in the browser, where it would inevitably drift from the server's projections. Invalidating and refetching the window was rejected because at the 20,000-Photo design target it re-reads from the anchor and visibly reflows, against the tracer budget that a displayed row never changes geometry.

The rule this generalises to is: **any mounted window whose collection the Photo just left withholds it, and every collection not currently mounted is invalidated in the history registry**. Archive and Restore are symmetric under it, a direct-route Viewer with no mounted window falls out as the degenerate case, and Photos arriving from background Upload Batch processing correctly leave the mounted Timeline untouched while refreshing the windows the User will return to. Consequences worth naming: a withheld descriptor is retained but unrenderable, so a reader will find entries the layout refuses to draw; the Date Index is marked stale and eagerly refetched rather than decremented locally, keeping one copy of the counting rule on the server at the cost of one small read per mutation; and the model deliberately cannot express *relocation*, which is why Adjust Captured At — where a Photo moves to another calendar period, possibly outside the loaded window — is excluded from this mechanism and needs its own design.
