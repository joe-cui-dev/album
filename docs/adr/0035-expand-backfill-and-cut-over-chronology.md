# Expand, Backfill, and Cut Over Chronology

Chronology migration will use an expand–backfill–cutover rollout with temporary v1 and v2 projection and API contracts rather than replacing the live representation in place. The expand release will make new writes and relevant mutations maintain v2 in side-by-side attributes while preserving the names and types consumed by the old reader; an idempotent backfill will populate and reconcile all legacy Ready Photos; the new Web client will then cut over to a separately versioned cursor API while the old endpoint and keys remain available for an observation and rollback period. Removing legacy items and compatibility fields will be a later explicit cleanup, so migration failure never requires restoring destructively overwritten chronology data or blocking uploads for the full backfill.

The Browsing tracer cuts the new Web client directly to the existing `/v2/timeline` and `/v2/archive` contracts. Thumbnail Access expiry is an additive v2 response field, and Viewer bootstrap is a new focused read rather than a v3 collection API. Legacy Timeline, Photo Detail, and Display Access reads remain during the observation period and are removed only by a later explicit cleanup after production smoke validation.

The later explicit cleanup landed 2026-07-25: the Legacy Timeline, Photo Detail, and Display Access reads and the v1 write path (the dual write in `process-photo.ts` and the `applyMigrationVersionV2` backfill) are all removed, along with the Phase 2 migration/reconciliation scaffolding this ADR's rollout depended on. This ran ahead of the planned order — before rather than after a production smoke test — because the app had already cleared all data and the User had confirmed a prior deploy (e6d5da0) was already smoke-tested; the retained v1 code was no longer a usable rollback once the Web client had cut over to v2, so recovery from either a bad migration or a bad cleanup is `git revert` and redeploy either way.

With the table still empty, the same cleanup promotes the surviving chronology representation to the unversioned canonical model: `TIMELINE#...` and `DATE_INDEX#...` replace the temporary `_V2` sort-key namespaces, and version suffixes are removed from store methods, shared contracts, handlers, routes, and tests. This is a direct reset rather than another backfill; once new Photos exist, future representation changes must again use an explicit migration decision rather than silently reinterpreting durable keys.
