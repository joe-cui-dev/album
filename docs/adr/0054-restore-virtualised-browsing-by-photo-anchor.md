# Restore Virtualised Browsing by Photo Anchor

Each Browsing Window history entry will restore against a content anchor consisting of the first substantially visible Photo ID and its Justified Row's offset from the content viewport, or a period anchor when a month marker owns the top position. Absolute scroll offset is only a same-layout fast path. Container width is an observation reported by the UI adapter. Before a meaningful width change is applied, the Browsing Window captures the current content anchor; it ignores repeated observations of the same effective width, coalesces meaningful changes, recomputes layout, finds the new row containing that Photo, and recreates the relative offset. If a mutation removed the Photo, restoration falls back to its remembered older neighbour, then newer neighbour, then period marker. It exposes that decision as a library-neutral restoration directive with a monotonically increasing revision. The UI adapter translates the directive into its virtualiser's scroll operation and includes `appliedRestorationRevision` in the resulting viewport observation. The Browsing Window completes restoration only when that revision equals the current directive; stale executions and acknowledgements are ignored. Ordinary observations without a revision may update demand and the saved anchor but cannot acknowledge restoration, and an observed User-initiated scroll cancels a pending restoration so programmatic correction never fights the User. The adapter does not choose the anchor, fallback, offset, resize policy, or whether a new directive supersedes an old one. Updates are throttled into the current history entry and never create scroll-generated history entries. This remains reliable when row indices and heights change across viewport sizes.
