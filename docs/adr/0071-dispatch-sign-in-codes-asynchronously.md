# Dispatch Sign-In Codes Asynchronously

Sign-In Code requests will enter a dedicated private queue and return the same accepted response without a public code identifier before email delivery, while a worker checks the User Allowlist and sends only for an Allowed User. Non-allowed requests follow the same public admission shape but become a no-op in the worker; verification uses Email Address plus Code and one generic invalid-or-expired result. This adds a queue and worker in exchange for removing response-body and synchronous SES timing signals that would otherwise reveal allowlist membership.

The breaking no-code-ID contract will enter through additive v2 request and verify routes. The new Web client cuts over while v1 remains for a 24-hour observation window, after which v1 is removed before MVP acceptance; existing Session reads and Sign Out remain unversioned.

On 2026-07-25, after the app's data was cleared, the compatibility window was closed by an explicit pre-MVP decision: no old browser tab or external API client needs continued support, and requiring refresh and re-authentication is acceptable. The asynchronous no-code-ID flow therefore becomes the sole canonical Sign-In contract at the unversioned `/session/sign-in-code` and `/session/verify` routes; the temporary v1 implementation, `/v2` route prefix, and version-suffixed implementation names are removed rather than preserved as permanent migration vocabulary.

The canonical Sign-In Challenge separates Code validity from record retention: a Code remains verifiable for ten minutes, while its send history remains available for at least the full rolling one-hour rate window even after the Code expires or is consumed. DynamoDB TTL therefore applies to the longer retention horizon rather than doubling as the Code-verification deadline; otherwise prompt TTL cleanup after ten minutes could incorrectly permit a sixth send inside the promised five-per-hour limit.

Because the metadata table is empty at this cutover, the surviving challenge record also adopts its final durable identity directly: `SIGN_IN#<normalised Email Address>` with sort key `CHALLENGE`. No compatibility reader or backfill is retained for the temporary v1 `SIGNIN#.../CODE#...` or v2 `SIGNIN2#.../CREDENTIAL` records.
